Context

See proposal.md for the motivation. The facts below come from finos/morphir-rust 945486e, finos/morphir-moonbit db63950 and finos/morphir 46052e3 (all main, 2026-10-29).

  • The crate. crates/morphir-gleam-binding has about 13,800 lines of Rust source and 6,300 lines of tests. It uses the untyped parser of gleam-core at gleam-lang/gleam 4a83802 (Gleam 1.18.1). It implements the SDK traits Extension, Frontend, Backend and Workspace, and exports them with export_extension! from morphir-extension-sdk.
  • It already builds to Wasm. The crate compiles to wasm32-unknown-unknown as an Extism plugin (MEP 0.1). Release extension/gleam/v0.3.0 in finos/morphir-rust ships an 11.3 MB morphir-gleam-binding-0.3.0.wasm, its .sha256 and a 2.0.0-draft.2 descriptor with runtime: "wasm". It has no attestation.
  • The Rust CLI. finos/morphir crates/morphir links the crate by path and registers it as the built-in native provider morphir-gleam (crates/morphir/src/extensions.rs).
  • The MoonBit CLI. It has no Gleam provider. Its portable route, core-wasm-process, runs a core-Wasm guest in a Node host through the profile morphir/mep-bytes-v1/v1-draft: imports morphir_bytes_v1.input_len, input_byte, output_byte; export handle() -> i32; MEP 0.2.0-draft.1 JSON-RPC bodies; at most 256 MiB memory and 10 s per call. Its extism-wasm route is fixed to Python and to macOS arm64. Its install commands accept only native executables from local directories.
  • The SDK. morphir-extension-sdk already implements MEP 0.2.0-draft.1 model operations as an opt-in (compile_model, generate_model, tuple negotiation, Ion inspection). The Gleam crate does not use them yet. The SDK has no morphir_bytes_v1 export.
  • Elm precedent. The Elm move to finos/morphir-elm is an uncommitted draft. It chooses a core-Wasm guest, a top-level moonbit/ directory, a git filter-repo import and a descriptor with runtime: "core-wasm". This design follows it where the languages allow.
  • This repository. It has Gleam packages, OpenSpec, a CI workflow with four required checks (Format Check, Type Check, Run Tests, Build Packages) and a CLI release workflow on v*.*.* tags and on release: created. It has no beads database; work is tracked in GitHub issues. The base branch is main (Damian confirmed; no vnext).

Goals and non-goals

Goals:

  • The crate, its tests and its history live in finos/morphir-gleam and build and test there without a checkout of another repository.
  • A tagged release produces an attested bundle that a repository index can admit by publisher identity.
  • The module runs in any host that implements morphir/mep-bytes-v1/v1-draft, including a browser.

Non-goals:

  • Changes to finos/morphir-moonbit, finos/morphir-rust or finos/morphir. They are planned in FUP-1 and need separate approval.
  • New Gleam language coverage (beads morphir-4q8g.*). That work moves here but is not part of this change.
  • Ion morphir-model output (see MEP-1).
  • The morphir extension publish command. The release workflow does its steps by hand and can call that command when it exists.
  • Rewriting the extension in Gleam or MoonBit.

Overview

Solid boxes are in this change. Dashed boxes are follow-up work in other repositories.

Decisions

RUN-1. Ship a core-Wasm guest, not a native process

The extension depends on Rust crates from the Gleam compiler, but that is not an obstacle to Wasm: the crate already compiles to wasm32-unknown-unknown and has a released 11.3 MB module. Only the host ABI changes.

A native process is the fastest way to get Gleam into today's MoonBit CLI, but it gives up the browser, which is the reason the MoonBit CLI is the main CLI. If the MoonBit host work in MGR-1 is late, a native artifact can be added to the same release later as a second artifact. This design does not build it.

The Extism artifact is not shipped from this repository. The Rust CLI is being sunset, and extension/gleam/v0.3.0 stays available in finos/morphir-rust for it.

RUN-2. Byte-channel adapter in this repository

Add a module core_wasm to the crate behind a Cargo feature core-wasm. It exports handle: it reads input_len() bytes with input_byte, passes the JSON-RPC body to the same SDK dispatcher that the Extism handle uses, writes the response with output_byte, and returns the length, 0 or -2 as the profile defines. The Extism export moves behind a feature extism that release builds do not enable, so the module has no extism:host/env imports. A CI step checks the import list with wasm-tools print.

Alternative: add the adapter to morphir-extension-sdk first. That is the better final home, because every Rust guest needs it, but it is a change to finos/morphir-rust. The adapter is about 100 lines. Keep it here now and move it to the SDK as follow-up.

Not sure: whether the SDK's JSON-RPC dispatcher can be called without extism-pdk. If it cannot, the adapter calls the Extension, Frontend and Backend methods through a small local dispatcher instead. I will check this first in the implementation (task 2.1).

MEP-1. Claim the JSON model tuple first

The MoonBit host runs only MEP 0.2.0-draft.1 sessions on the core-Wasm route. It accepts two tuples: morphir-model / ion-binary (its default) and morphir-ir / morphir-json. The crate already produces Morphir IR v4 JSON, and the SDK has the JSON tuple. So the guest implements Frontend::compile_model and Backend::generate_model for the JSON tuple only. Users select it with --model-format json.

Alternative: Ion morphir-model now. That profile carries source and naming provenance that the Gleam frontend does not record yet. It is a separate change with its own spec delta.

MGR-1. No MoonBit assembly manifest in the bundle

The MoonBit host needs manifest.ion next to model.wasm. Its schema, morphir-assembly-artifact-v1-draft, requires a MoonBit package graph and MoonBit compiler and SDK digests. A Rust guest cannot fill these fields with true values. The bundle therefore has only the module and the descriptor. The descriptor states runtime: "core-wasm" and executionProfile and lists both in critical, so that readers that know only process and wasm (Extism) refuse the artifact instead of misloading it.

The MoonBit CLI must accept a guest without a MoonBit manifest, or define a language-neutral manifest that the release workflow can then produce. This is follow-up work in finos/morphir-moonbit (FUP-1). Until it lands, the 0.4.0 bundle is correct and attested but no MoonBit CLI can run it. The host test in TST-1 proves the module against the profile.

LAY-1. Rust half under rust/

morphir-gleam/
├── packages/                       Gleam packages (unchanged)
├── rust/
│   ├── Cargo.toml                  workspace, members = ["crates/*"]
│   ├── Cargo.lock
│   ├── rust-toolchain.toml         channel + wasm32-unknown-unknown
│   └── crates/morphir-gleam-binding/   imported crate (src, tests, fixtures, goldens)
│       └── claims/expected.json    committed expected claims
├── .config/mise/config.rust.toml   rust, wasm-tools, cargo tools (MISE_ENV=rust)
├── .config/mise/tasks/rust/        build, test, wasm, host-test, bundle, claims
└── .github/workflows/gleam-extension.yml, gleam-extension-release.yml

A subdirectory keeps the Gleam root clean, gives CI one path filter, and matches the Elm draft's moonbit/. Rust tools go in a separate mise environment so the Gleam jobs do not install Rust. The crate keeps its name so the imported history and the finos/morphir path dependency stay readable until removal.

Alternative: a root Cargo.toml with crates/. It mixes two build systems at the root and makes path filters wider.

HIS-1. Import the history with git filter-repo

The crate has 47 commits and was never renamed, so history import is practical:

git clone --no-local finos/morphir-rust /tmp/gleam-import
git -C /tmp/gleam-import filter-repo \
  --path crates/morphir-gleam-binding \
  --path-rename crates/morphir-gleam-binding/:rust/crates/morphir-gleam-binding/ \
  --message-callback '…remove AI co-author trailers, add Imported-from trailer…'
git fetch /tmp/gleam-import main:import/gleam-binding
git merge --allow-unrelated-histories --no-ff import/gleam-binding

EasyCLA checks every commit in a pull request. The filtered history has four commits with Co-Authored-By: Claude trailers and one with a copilot-swe-agent[bot] trailer. The message callback removes those trailers and adds Imported-from: finos/morphir-rust@<original sha> to every commit, so the original record stays one lookup away. The other authors are Damian (45 commits) and renovate[bot] (2 commits).

The pull request must be merged with a merge commit, not squashed. The repository allows merge commits and does not require linear history. Squash merge would drop the history. Damian approved this import on 2026-10-30 and asked the implementer to do the merge of PR 1, with a merge commit, after review and CI pass. All other pull requests still wait for Damian's explicit merge approval.

Not sure: whether EasyCLA accepts the two renovate[bot] commits. Renovate pull requests are merged in this repository, so I expect yes. If not, the callback can drop them, because they only changed dependency versions.

DEP-1. Use the published Morphir Rust crates

  • morphir-extension-sdk 0.4.0, morphir-core 0.2.0 and morphir-workspace 0.2.0 come from crates.io, with their published dependencies morphir-json 0.2.0 and morphir-config 0.0.1. On 2026-10-30 no crate had a commit on finos/morphir-rust main after its publish time, so the published versions equal the source the crate builds with today.
  • morphir-common is not published and is native-only. The crate uses only its VFS (MemoryVfs, OsVfs, Vfs). Copy that small part into src/vfs.rs and drop the dependency.
  • gleam-core: keep the git revision. Move the Renovate rule for it from finos/morphir-rust to this repository.

When this repository needs a change in those crates (for example the adapter move in FUP-1), finos/morphir-rust makes and publishes it first, by its crate-tag workflow. This repository then raises the version. Alternative: git dependencies pinned to a revision. They are not needed, because the published versions are current, and they would tie builds to the availability of that repository.

ID-1. Keep morphir-gleam and continue at 0.4.0

The id morphir-gleam, short id gleam and tag scheme extension/gleam/v* stay. There is only one Gleam implementation, so a qualified id such as the Elm draft's morphir-elm-moonbit is not needed. Docs, bead morphir-ukvn.5.64.28 and the MoonBit repository proposal already use morphir-gleam. The first release here is 0.4.0: the ABI change from Extism to core Wasm breaks hosts of 0.3.0, and a 0.x minor bump says so. The artifact name changes from morphir-gleam-binding-<v>.wasm to morphir-gleam-<v>.wasm so that it matches the id.

Tag names are per repository, so extension/gleam/v0.4.0 in finos/morphir-gleam does not collide with extension/gleam/v0.3.0 in finos/morphir-rust. An index records both by owner/repo.

CI-1. Change-scoped CI

A new workflow gleam-extension.yml runs on pull requests and pushes to main when these paths change: rust/**, .config/mise/config.rust.toml, .config/mise/tasks/rust/**, .github/workflows/gleam-extension*.yml and the bundle script. Jobs: fmt and clippy, test, wasm (build, validate, import check, host test, claims check, upload the module as a build artifact), and bundle-dry-run (assemble the bundle without attesting or publishing).

The four existing required checks do not change and still run on every pull request. The new jobs are not made required, because a path-filtered workflow that does not run would block merges. A later change can add one always-running summary job and make it required.

REL-1. Release workflow and attestations

gleam-extension-release.yml runs on tags extension/gleam/v* and on workflow_dispatch with a tag and a publish flag (default false, for dry runs).

  1. check: the tag commit is reachable from main; the tag version equals the crate version.
  2. build (Linux, once): build the module; upload it as a workflow artifact.
  3. test (matrix Linux, macOS, Windows): download that module; run the host test and claims check on it. Linux also runs cargo test.
  4. publish (Linux; permissions contents: write, id-token: write, attestations: write): write release.json with claims from a live describe; write each .sha256; run sha256sum --check; run actions/attest@v4 on the module and on release.json; run gh attestation verify --signer-workflow on both; then gh release create "$TAG" --verify-tag --latest=false with the four files.

Other jobs have contents: read only. The bundle script is a bun TypeScript mise task, like the other tasks in this repository. When morphir extension publish exists, the publish job calls it instead.

The CLI workflow release.yml also runs on release: created. Without a guard it would build Gleam CLI binaries and upload them to the extension release. Add if: ${{ !startsWith(github.event.release.tag_name, 'extension/') }} to its first job. Its tag filter v*.*.* does not match extension/gleam/v0.4.0, because * does not match /.

FUP-1. Follow-up in other repositories (not made here)

finos/morphir-moonbit (needed before the bundle is useful). The first two items are a fast follower of this change: start them when PR 2 has merged, so that the 0.4.0 module can be run by the MoonBit CLI soon after its release.

  • Run a core-Wasm guest that is not built from MoonBit: accept the bundle without manifest.ion, or define a language-neutral manifest.
  • Document-tree support (fast follower). The core-Wasm route sends one document and fixes languageId: "moonbit". A Gleam project is a tree of modules under src/ that import one another, and the guest already accepts several documents in one compile request (multi_document). The host must send the whole source tree as documents with relative paths and the language id from the claims, and must respect the request size limits for it. The guest side of this is tested in this change (multi-module fixtures in the host test).
  • Read runtime: "core-wasm" descriptors and install core-Wasm bundles from a repository (install accepts only native executables today).
  • Add a host test that runs the released Gleam module; rework bead morphir-ukvn.5.64.28 to use the installed extension.
  • Optional: the browser host route for the same module.

finos/morphir:

  • Add morphir-gleam to the extension index with trusted publisher finos/morphir-gleam and workflow .github/workflows/gleam-extension-release.yml, when the index exists.
  • Remove the built-in provider and the gleam subcommand from the Rust CLI, or let them go with the CLI: crates/morphir/Cargo.toml path dependency, src/extensions.rs, src/commands/gleam.rs and the compile, UI and help files that name it, Gleam tests in crates/morphir/tests/, examples/gleam/*, and docs/cli/gleam*.   • Update the ecosystem/morphir-gleam submodule pin (aa2b7e2, January 2026).
  • Beads: close or rewrite morphir-ukvn.1.4 to point at this change; update the blockers of .1.8 and .1.9; move morphir-4q8g.* to finos/morphir-gleam issues.

finos/morphir-rust:

  • Remove crates/morphir-gleam-binding, [extensions.gleam] in .github/extensions.toml, .mise/tasks/extension/artifact/gleam, crates/morphir-host-native/tests/gleam_extension.rs, the gleam-core rule in renovate.json, the Gleam line in .gitattributes, and the Gleam parts of README.md and docs/.   • Move the byte-channel adapter into morphir-extension-sdk and publish a new SDK version by the crate-tag workflow; then this repository uses it and deletes its local adapter.

Migration plan

  1. PR 1: history import (merge commit), rust/ workspace, crates.io dependencies, VFS copy, mise environment, change-scoped CI with native tests. The crate is still the 0.3.x Extism crate.
  2. PR 2: core-wasm adapter, MEP 0.2 model operations, Wasmtime host test, expected claims, version 0.4.0.
  3. PR 3: release workflow, bundle script, release.yml guard, README, AGENTS.md and CHANGELOG. Run the release workflow with publish: false.
  4. Tag extension/gleam/v0.4.0 only after you approve it.
  5. Follow-up changes in other repositories, each after your approval.

Rollback: nothing outside this repository depends on the new code until FUP-1, and extension/gleam/v0.3.0 stays in finos/morphir-rust. A bad release can be deleted before an index admits it.
